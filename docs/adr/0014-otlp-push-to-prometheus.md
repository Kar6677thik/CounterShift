# ADR 0014: Metrics via OpenTelemetry, pushed over OTLP to Prometheus's native receiver

- **Status:** Accepted
- **Date:** 2026-10-17
- **Spec:** §3 ("/metrics" and Prometheus), §7.5. **This changes the spec**, which assumed a scraped `/metrics` endpoint.

## Context

The spec planned a `/metrics` endpoint for Prometheus to scrape (the *pull* model). In .NET that endpoint comes from `OpenTelemetry.Exporter.Prometheus.AspNetCore`, which is **still prerelease** (`1.20.0-beta.1`, October 2026). The OTLP exporter is stable (1.20.0). Prometheus 3.x accepts OTLP writes natively (`--web.enable-otlp-receiver`).

## Decision

- Instrument with `System.Diagnostics.Metrics` (already done in M6). Collect with the OpenTelemetry SDK: ASP.NET Core HTTP metrics, runtime metrics, `CounterShift.Storage` and `CounterShift.Api`.
- **Push** over OTLP/HTTP-protobuf every **5 s** to `http://<prometheus>/api/v1/otlp/v1/metrics`.
- Export is enabled only if `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` (or the generic `OTEL_EXPORTER_OTLP_ENDPOINT`) is set. The app logs at startup whether export is on and where it goes.
- The endpoint and protocol are **set explicitly in code**: `AddOtlpExporter()` ignores the per-signal environment variable (see "Found while building").
- Explicit histogram buckets from 0.5 ms to 2.5 s for HTTP and storage durations. ASP.NET Core's defaults start at 5 ms, which is too coarse for a p99 in single-digit milliseconds.
- Grafana has a provisioned datasource and a **dashboard generated by `deploy/observability/build_dashboard.py`** (dashboards as code).

## Pull vs push: what we gave up and what we got

| | Pull (scrape `/metrics`) | Push (OTLP) — chosen |
|---|---|---|
| Package maturity in .NET | prerelease | **stable** |
| Discovering targets | Prometheus must find every pod (Kubernetes service discovery) | every pod sends to one URL |
| "Is the target up?" | free (`up` metric) | must be inferred from data arriving |
| Path to traces and logs later | separate | same protocol, same SDK |
| Inspect metrics with curl | yes | no (use Prometheus) |

## Consequences

- Metric names follow Prometheus's OTLP translation: `cs.storage.operation.duration` (s) → `cs_storage_operation_duration_seconds_*`, and labels change `.` to `_` (`http.route` → `http_route`). Pod identity comes from `service.instance.id` → `instance`.
- If Prometheus is down, the app keeps working, and that interval's metrics are lost.
- Counters that have never been incremented don't exist in Prometheus. Dashboards use `or vector(0)` where "zero" is the expected state.

## Found while building (worth remembering)

1. The app's export log said the endpoint was set, yet nothing arrived. The OpenTelemetry **self-diagnostics** log (an `OTEL_DIAGNOSTICS.json` file *in the app's base directory*) showed the exporter posting to `localhost:4318`, the default. The per-signal variable is ignored by `AddOtlpExporter()`. Lesson: log what a component *actually uses*, not what you passed it.
2. On this Windows machine, `localhost:59090` over IPv6 is owned by `wslrelay.exe` (WSL's localhost forwarder), while Docker serves IPv4. Use `127.0.0.1` for local endpoints.
